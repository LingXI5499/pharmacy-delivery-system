## 3. 任务明细

### P0：集成治理与冲突控制

需求：

- 为每个任务建立独立分支、worktree 和 PR，PR 目标为 `codex/v2-enterprise-upgrade`。
- 维护任务状态、合并顺序和冲突清单。
- 独占 `.github/workflows/ci.yml`、公共依赖版本和最终 JaCoCo 配置。
- 每次合并后运行完整 CI，失败立即停止后续合并。

验收：

- 所有功能提交都能关联唯一任务 ID。
- 没有 Agent 直接修改 `main` 或原始脏工作树。
- PR 说明包含测试证据、风险和未完成事项。

### Q1：Security 与处方安全测试

需求：

- 覆盖未登录 401、角色不足 403、越权处方访问不泄露资源存在性的 404/拒绝。
- 验证 Access Token 过期刷新、Refresh Token 轮换、旧 Token 重放导致令牌族撤销、退出后的 Access Token 拒绝。
- 验证处方伪造扩展名、错误 MIME、超限、空文件、路径穿越、非本人下载和药师权限。
- 文件测试必须使用临时目录，结束后清理，不写入静态资源目录。
- 只在测试暴露真实缺陷时修改 `security` 或 `prescription` 生产代码。

验收：

- 安全测试可重复执行且不依赖开发者已有数据。
- 日志、响应和审计记录不包含密码、Refresh Token、文件真实路径。
- 新增测试对相关服务的关键分支形成有效覆盖，而非只验证 HTTP 200。

### Q2：支付退款幂等与故障测试

需求：

- 同一支付回调并发或重复 10 次，只发生一次订单状态变化和一次库存流水。
- 同一退款回调重复 10 次，只完成一次退款；发货前按规则回补，配送中或完成订单不得错误回补。
- 非订单所有者不能调用模拟支付；非法状态、金额不一致和不存在记录必须拒绝。
- 验证支付、订单、预占、流水任一步异常时事务一致性。
- 如发现唯一约束或锁不足，先提交兼容设计给 P0；不得抢占 V4 迁移编号。

验收：

- 使用真实 MySQL 验证数据库唯一键，而非仅 mock Mapper。
- 每个重复事件均能给出最终订单、支付/退款记录、批次库存和流水断言。

### B1：库存盘点、差异对账与近效期闭环

需求：

- 新增 `inventory_count`、`inventory_count_item`，状态固定为 `DRAFT → COUNTING → COMPLETED`，终止状态 `CANCELED`。
- 盘点项保存批次账面量快照、实盘量、差异量、原因和操作人。
- 完成盘点时锁定批次；重复完成不得重复调整；差异通过库存服务追加 `STOCK_COUNT` 流水。
- 新增对账查询：`medicine.stock` 与所有可售批次可用量总和不一致时返回差异，但不得自动静默修正。
- 近效期支持 30/60/90 天筛选，排除过期、隔离和不可售批次。
- 使用 `V4__inventory_count_reconciliation.sql`，不能修改 V1～V3。
- 完成仓库端盘点、差异确认、对账和近效期页面。

验收：

- 两人或两个请求同时完成同一盘点单，只能成功一次。
- 差异调整后批次、聚合库存和流水一致。
- 盘点失败时不产生部分库存变化。
- 空库与 V1 升级路径全部通过。

### F1：采购与仓库前端闭环

需求：

- 采购员能够维护供应商、创建采购单、查看明细和状态。
- 管理员能够审批或拒绝采购单并填写原因。
- 仓库人员能够针对已审批采购单执行分批收货，录入批号、生产日期、效期、采购价、合格数和拒收数。
- 页面明确展示未收数量、部分收货和完成状态，前端校验不得代替后端校验。
- 保留现有视觉体系，不整体重做 UI。

验收：

- Vue/TypeScript 构建通过。
- 不同角色无法通过路由或直接调用看到不属于自己的操作。
- 页面错误信息来自统一 API 错误模型，不吞异常。

### E1：Playwright E2E 与演示数据

需求：

- 引入 Playwright，建立独立、可重复的虚构演示数据初始化方式。
- 覆盖普通药下单支付、处方药上传审核、采购审批收货、FEFO 跨批次、订单超时、退款、角色越权。
- 测试失败保存截图、Trace、浏览器日志；成功时不提交生成物。
- 新增独立 `e2e.yml`，使用原生 MySQL/Redis/RabbitMQ，不使用容器。

验收：

- 无人工点击即可在 GitHub Actions 运行。
- 核心流程断言数据库或最终 UI 状态，不只断言页面元素存在。
- 测试数据不会污染开发数据库。

### O1：可观测性、备份恢复与运维演练

需求：

- 输出结构化日志，稳定携带 Trace ID、用户 ID、业务 ID、错误码，禁止记录令牌和处方内容。
- 提供 Prometheus 和 Grafana Linux 原生配置、核心指标与仪表盘导出文件。
- 增加数据库备份、校验、恢复脚本和演练文档；脚本必须拒绝空目标、生产默认值和危险路径。
- 记录 Redis/RabbitMQ/MySQL 故障诊断步骤、告警阈值和恢复标准。

验收：

- 能从一次请求定位到订单、库存和消息事件。
- 在临时数据库完成备份后恢复，并校验关键表行数及校验和。
- 仪表盘至少覆盖 JVM、HTTP、连接池、订单失败、未完成事件和库存冲突。

### P1：k6、慢 SQL 与索引优化

需求：

- 准备可重复生成的数据集和 k6 脚本，执行 100 VU、持续 10 分钟。
- 读接口目标 p95 < 500ms，下单接口 p95 < 1s，错误率 < 1%，库存正确性优先。
- 保存硬件、数据量、脚本、原始结果、慢 SQL、`EXPLAIN ANALYZE` 和优化对比。
- 只有证据证明收益时才新增 `V5__performance_indexes.sql`；禁止凭感觉堆索引。
- 性能工作流应手动或定时运行，不能让每个普通 PR 都等待 10 分钟压测。

验收：

- 压测结束后库存、订单、预占和流水对账为零差异。
- 报告明确未达到的指标，不删除失败结果。

### Q3：覆盖率提升与强制门禁

需求：

- 在已合并功能上补齐订单、库存、权限、处方、支付、退款、消息和采购测试。
- 优先测试业务分支、回滚和安全边界，不为覆盖 getter/setter 编写无价值测试。
- 分阶段启用门禁：先全项目 50%，再提升至全项目行覆盖率 70%；核心 Service 分支覆盖率达到 80%。
- JaCoCo 排除项只允许配置生成代码或框架入口，并在 PR 中列出理由。

验收：

- CI 自动失败于覆盖率下降。
- 报告可下载并包含模块/包维度数据。
- 达标数字来自同一 CI 提交，而不是本地旧报告。

### D1：文档、复盘与面试材料

需求：

- 补齐 PRD、用例、ER 图、权限矩阵、状态图、关键时序图、OpenAPI 使用说明。
- 输出至少三份 ADR：模块化单体、可靠事件、为何不拆微服务。
- 输出 Redis、RabbitMQ、库存并发各一份故障或设计复盘。
- 整理 SQL 优化、性能、部署、备份恢复手册和虚构演示账号说明。
- 形成简历项目描述及 3/5/10 分钟面试讲稿，使用“问题—约束—方案—失败方案—测试—结果”结构。

验收：

- 文档中的每个性能、覆盖率和可靠性数字都能链接到对应 CI 或报告。
- 不将未完成能力、教学数据或架构设想描述成真实生产经验。

## 4. 推荐执行波次

### 第 1 波：第 1～2 周

- P0 先建立分支、Issue、文件所有权和合并队列。
- Q1、Q2、F1 三个 Agent 并行。
- 合并顺序：Q1 → Q2 → F1，每次合并后运行完整 CI。

### 第 2 波：第 2～4 周

- B1 在 Q2 合并后开始，独占 V4。
- O1 与 B1 并行，但不修改库存生产代码和主 CI。
- 合并顺序：B1 → O1。

### 第 3 波：第 4～6 周

- E1 基于完整采购和盘点 UI 建立 E2E。
- Q3 开始补测试，但最终门槛必须等待 E1、B1 合并。
- P1 在 B1 数据结构稳定后执行。

### 第 4 波：第 6～9 周

- Q3 达到覆盖率目标并启用门禁。
- D1 汇总真实报告、ADR、面试材料。
- P0 执行最终回归、审查未完成项并决定是否合入 `main`。**结论：不合入 `main`，阶段性演示版。** [p0-final-gate.md](p0-final-gate.md)

## 5. 最终发布门禁

- 后端单元与原生 MySQL 集成测试全绿。
- 前端构建、依赖审计和 Playwright E2E 全绿。
- 空库和 V1 升级迁移都通过。
- 全项目行覆盖率 ≥ 70%，核心 Service 分支覆盖率 ≥ 80%。
- k6 报告完成并执行压测后数据库对账。
- Redis、RabbitMQ、备份恢复故障演练有日志和复盘。
- PR 无高优先级审查问题、无明文凭据、无虚假项目描述。

未满足上述条件时，可以发布“阶段性演示版”，但不得标记为“完整稳定版”。
